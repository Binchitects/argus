## 0. What exists today

### Argus and GitLab

**Argus's token is read-only already.**
- `ARGUS_GITLAB_TOKEN` (or a token Argus mints from a password) carries `read_api` + `read_repository`. It is "never handed to a developer, never leaves the host" (docs/argus/README.md "Authentication", "When no token can be issued").
- `tools/test-gitlab/seed.py` makes `argus_reader` with exactly those scopes, as Reporter on every project.

**How Argus decides what a person may see** (src/Argus/Access/Acl.cs):
- The app calls Argus with `ARGUS_KEY` and the header `x-llm-user-email` (src/Llm.Api/Chat/ArgusMcp.cs:488-497).
- `People.GrantFor` (Acl.cs:339) finds the GitLab user by email, then by username.
- It reads `/projects/{id}/members/all` with the service token and grants a project when that user is an active member at **Reporter (20) or above** (Acl.cs:33, :367).
- `MemberDirectory` keeps the result 10 minutes and serves it stale for up to 1 hour while GitLab is down. It also exposes access levels and `Maintainers()` (Acl.cs:138-285).
- `PersonAccess` (Acl.cs:438) checks only the repository rows in Argus's index (`People.Repos`).

Two limits follow:
- A project that is **public or internal but not a membership** is denied.
- A project that is **discovered but not indexed** cannot be checked.

**Git mirrors.** Argus fetches only `+refs/heads/*` (src/Argus/Indexing/Mirror.cs:161). Merge request refs are not fetched.

**Argus's webhook** (`/hook/gitlab`, ArgusServer.cs:428-490):
- It accepts push events, and merge request events only when the request is **merged**. Other events are acknowledged and ignored.
- A Maintainer or group Owner creates it once, by hand. Argus's own token stays read-only.

**The app's GitLab bot** (src/Llm.Api/Schedules/Triggers.cs):
- `GitLabBot` uses a **bot token with `api` scope** (`GitLab:BotToken`). It reads `/merge_requests/{iid}/changes` and job traces, and posts notes.
- Scheduled tasks can run "On GitLab events" through `/api/hooks/<id>` and "Answer as a comment in GitLab" (chat.md "Scheduled tasks").
- Company knowledge also reads GitLab wikis and issues with this bot token.
- **This conflicts with the person's constraint.** The design below does not depend on the bot.

**CI review already exists.** `clients/arena/arena review` and `clients/gitlab-ci/arena-review.yml` run inside the project's own pipeline with a project access token (docs/ci.md).

### What the app already has

- **Per-person secrets.** `PersonCredentials` stores tokens encrypted with `APP_DATA_KEY` and refreshes OAuth tokens (src/Llm.Api/Plugins/PersonCredentials.cs). It is reused below for each person's own GitLab token.
- **Safeguards.**
  - `Secrets.Find/Mask` (src/Llm.Api/Safeguards/Secrets.cs) knows GitLab `glpat-`, GitHub, AWS, private keys and more.
  - Each group sets refuse/mask/off for secrets (settings.md, "What a group can set").
- **Notifications.** `Notifier.SendAsync(userId, News(kind,…))` plus Web Push.
- **Arena MCP.** `McpTools` serves each person's own tools, runs them as that person, and audits each call (src/Llm.Api/ArenaMcp/McpTools.cs:25-60).
- **Diff viewers.**
  - Monaco's diff editor in Code Arena: `src/web/src/code-arena/editor.tsx:1227` and `compare.ts`. Monaco is bundled with self-hosted workers (`monaco.ts`).
  - A Myers line diff in the chat: `src/web/src/pages/chat/canvas-diff.ts`.
- **Tests.**
  - Argus.Tests has `FakePlatform`, which fakes the app's key check and GitLab's `/users` and members endpoints, with delay and down switches (SlowGitLabTests.cs). There is also a `FakeGitLab` in GitLabSignInTests.cs.
  - Llm.Tests has `FakeArgus` (an HttpMessageHandler covering `/mcp` and `/admin/*`).
  - Neither fakes the merge request API.
  - The real test GitLab (`tools/test-gitlab/run.sh`) is the end-to-end option. It is down now and needs Podman, since Docker Hub is blocked.

### Access control today

- **One Identity role pair**, `admin` and `member` (src/Llm.Core/Identity/AppUser.cs:86-91).
  - 21 endpoint groups use `AdminEndpoints.Policy`, which is `RequireRole(admin)`, IdentityWiring.cs:137.
  - About 23 inline `IsAdmin` checks remain.
  - The admin role is also set from LDAP, OIDC or SAML "Admin group" settings (CompanySignIn.cs:134, SettingsCatalog `Ldap:AdminGroup`).
- **Resource audiences.** Tools, local models and knowledge sources carry `Audience` (Everyone, Admins or Groups) plus `Groups`. `Membership.May` lets admins bypass all of them (src/Llm.Api/Access/AccessService.cs:11-19).
- **Model access at the gateway.** `KeyAccess` pushes each person's allowed models onto their LiteLLM keys.
- **Person flags.** `IsDisabled` and `ApiOff`.
- **Group policies.** Retention, safeguards and rate limits per key, each combined across groups as shortest, strictest or highest (settings.md:120). Credits per kind (chat, api, pictures, video, speech; Credits.cs) per person and per group, plus priority and cost centre.
- **Argus's own pages** check `CurrentUser.IsAdmin` (src/Argus/Platform/PlatformApi.cs:301). The app's Argus admin pages are behind the admin policy.
- **Rooms.** The rooms design (design-rooms.md) adds per-room owner, member and viewer roles, with `RoomAccess` replacing `Owned()`.

## 1. Architecture: where each part lives

```
Browser (review page, assistant, rooms) ─┐
Code Arena (/review, review open)  ──────┼─► App (Llm.Api)
Other agents (Arena MCP)  ───────────────┘     • Access.Check (one decision point, phase A)
                                               • Review engine (jobs, model calls, credits, safeguards)
                                               • Rooms / review threads / notifications / audit
                                               • Person's own code-host token (PersonCredentials) → post back, open MR
                                               │  ARGUS_KEY + x-llm-user-email (+ the person's repository rules)
                                               ▼
                                             Argus
                                               • CodeHost abstraction: GitLab | GitHub | Gitea | plain git
                                               • read-only service credential (never leaves Argus)
                                               • PersonAccess: GitLab rights ∩ app rules
                                               • MR reads, compare, file at any commit, git grep at a commit
                                               • polling + webhook → events to the app
```

**Decision: Argus does all reads from the code host; the app never holds a code-host credential except the person's own.**

Reasons:
- The read-only token is already in Argus, and its handling is documented (CA, TLS, password minting, refresh on 401).
- `PersonAccess` already enforces each person's rights.
- Coding agents connected to `argus.DOMAIN/mcp` get the same merge request tools for free.

## 2. Reading merge requests with a read-only token

### What `read_api` + `read_repository` allow

With the service account as Reporter, every call below is a GET (or a git fetch), so no write scope is needed:

| Need | GitLab call |
|---|---|
| List open MRs | `GET /projects/:id/merge_requests?state=opened&updated_after=&order_by=updated_at` |
| MR metadata | `GET …/merge_requests/:iid` (`diff_refs` {base,start,head}, author, reviewers, labels, draft, `detailed_merge_status`, `head_pipeline`) |
| Diff | `GET …/merge_requests/:iid/diffs` (paged, GitLab ≥15.7; fall back to `/changes`); `GET …/versions` and `/versions/:id` (pushes over time, which feed re-review) |
| Commits | `GET …/merge_requests/:iid/commits` |
| Discussions | `GET …/merge_requests/:iid/discussions` (with diff positions and resolved state) |
| CI | `GET …/merge_requests/:iid/pipelines`, `GET /projects/:id/pipelines/:pid/jobs`, `GET /projects/:id/jobs/:job/trace` (Reporter may read logs unless the project restricts pipelines) |
| Approvals (EE) | `GET …/merge_requests/:iid/approvals`, when present |
| Branch or range | `GET /projects/:id/repository/compare?from=&to=&straight=false` |
| Files at a commit | git: `fetch origin refs/merge-requests/:iid/head` into the mirror, then `git show sha:path`, `git grep sha`. API fallback: `/repository/files/:path/raw?ref=sha` |
| Who may see it | `/projects/:id/members/all` (already in use) and `/projects/:id` (`visibility`) |

### Gaps and fixes

1. **Merge request refs.** Argus fetches a single ref on demand, `git fetch origin +refs/merge-requests/<iid>/head:refs/arena/mr/<iid>`, into the existing mirror. It is pruned when the MR closes or after 30 days.
   - A project with no mirror (left out of the index) gets a fetch-only mirror. Nothing is indexed for it.
2. **Rights for projects that are not indexed.** `People.Repos` lists discovered rows (`repo_choices`) as well as indexed ones, so review and assistant tools can check projects that are left out.
   - Proposed default: a left-out project can be reviewed but not code-searched. **Decision R1.**
3. **Visibility.** Today only members at Reporter or above pass. **Decision R2:**
   - keep it strict (my default); or
   - also allow `internal` projects to any active GitLab account, and `public` projects to everyone, with visibility read from `/projects/:id`.
4. **Writes** never go through Argus.

### Code-host abstraction (in Argus)

```
interface ICodeHost {
  Kind (gitlab|github|gitea|git)
  ListChanges(project, state, updatedAfter, page) → ChangeRequest[]
  GetChange(project, number) → ChangeRequest {diffRefs, versions, pipeline, approvals}
  Diff(project, number | from..to, version?) → FileDiff[]
  Commits(project, number | from..to)
  Discussions(project, number)
  Ci(project, number | sha) → Pipeline{jobs}; JobLog(project, job, tailBytes)
  FetchRef(project, ref) → sha   // into the mirror
  Members(project) → (user, level)   // per-person rights
}
```

| Host | Per-person rights |
|---|---|
| GitLab | Today's `MemberDirectory`. |
| GitHub, Gitea | A read-only token (fine-grained "Contents: read, Pull requests: read, Metadata"). Listing collaborators on GitHub needs push access, so per-person rights come from the person's own linked token (`GET /repos/…` as them) or org teams read with `read:org`. **Decision R3.** |
| Plain git | A URL plus a read-only deploy key or token set by an admin. No host rights exist, so rights come only from the app's repository rules (phase A). Reviews of a range or branch only. |

### New Argus surface

Each route is offered two ways:
- as internal HTTP for the app, at `/review/*` with `ARGUS_KEY` and the email;
- as MCP tools for agents.

All of them are gated by `PersonAccess` plus the person's rules.

Tools: `mr_list`, `mr_get`, `mr_diff` (path filter, `since_sha` for interdiffs), `mr_commits`, `mr_discussions`, `ci_status`, `job_log` (tail, secrets masked), `compare_refs`, `file_at` (path@sha, line range), `grep_at` (git grep at a sha, for branches that are not indexed), `apply_check` (applies a patch to a temporary worktree at a sha and returns the resulting files or conflicts, with no network).

The existing `find_references`, `change_impact`, `impact_of`, `code_contracts` and `semantic_search` give context from the indexed target branch.

### New events

- **Polling (the floor).** Argus polls `merge_requests?updated_after=` once per *watched* project every `ARGUS_MR_POLL` (default 3 min, one call per project).
- **Webhook (optional).** The existing `/hook/gitlab` also forwards MR open, update, close and merge, pipeline, and note events. Merged events still index as they do now.
- **Delivery.** Events go to the app through `POST app:8080/api/internal/code-events` with `ARGUS_KEY`, deduplicated by (project, iid, head_sha).
- **Constraint.** The webhook needs a Maintainer once. If nobody can create one, polling alone works.

## 3. The review engine (in the app, `src/Llm.Api/Review/`)

**Runs.**
- A `ReviewRun` is a background job with its own runner, lighter than `AnswerJobs` and without a conversation.
- It takes a place through `AnswerGate` at the requester's priority, minus one, so interactive chats go first.
- Model calls go through the gateway with `user = requester email`.

### Pipeline

1. **Snapshot.** `mr_get` and `mr_diff` give `diff_refs`, the files, hunks, commits, CI, discussions and description.
   - Generated, vendored, lock and binary files, and files over 2k changed lines, are skipped and listed. Argus already knows vendored files (migration 009).
   - A size cap applies (admin setting, default 3,000 changed lines or 150 files). Above it the requester sees an estimated cost and must confirm.
2. **Safeguards on the input.**
   - `Secrets.Find` runs on added lines.
   - Every hit becomes a **blocker finding, made by the code and not by the model** ("Secret committed: GitLab token at x.cs:12"). It shows the kind and a masked value, never the value.
   - The model input is masked by the requester's group policy. "Refuse" stops the run with a reason.
   - Personal-data masking applies as in the chat.
   - The diff, commit messages, MR text and discussions are wrapped as data, with an instruction that text inside them is not instructions (prompt injection).
3. **Conventions.**
   - Read with `file_at`: `ARENA.md`, `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING*`, `.editorconfig`, linter configs (`.eslintrc*`, `ruff.toml`, `.clang-format`, `Directory.Build.props`, `stylecop.json`), `CODEOWNERS`.
   - Each project can add instructions in its review policy.
4. **Units.** Changes are grouped by file, or by a set of related files (a symbol changed in one and used in another, from Argus `change_impact`), each within a token budget. Each unit gets:
   - the hunks with ±N context lines;
   - each changed function in full, at head, from `file_at`;
   - callers and callees from `find_references` on the target branch;
   - tests touching the file, found by name and reference.
5. **Review pass**, one per unit, in parallel up to N.
   - The model has read-only tools: Argus's tools pinned to the project and the head sha. It has no posting tools.
   - Output is JSON: `findings[{path, side: new|old, line, end_line, severity: blocker|major|minor|nit, category: correctness|security|tests|conventions|performance|maintainability, title, body, suggestion_patch?, confidence 0-1}]`.
   - Instructions: categories with examples; "report only what you can point to in the diff"; "conventions means *this repository's* rules, cited".
6. **Anchoring.** Each finding is mapped onto the hunks:
   - new-side lines must be added or context lines;
   - old-side lines must be removed lines.

   Its GitLab position is stored as `{base_sha, start_sha, head_sha, old_path, new_path, old_line, new_line}`, so posting back needs no conversion. A finding that does not anchor moves to "General" (file level, or MR level).
7. **Verification (the adversarial pass).** A second prompt runs per finding, optionally on a different model (admin setting).
   - Prompt: "Try to refute this. Read the code (tools allowed). Answer refuted, confirmed or uncertain, with evidence."
   - Refuted findings are dropped but kept, hidden behind "Show N refuted" for calibration.
   - Uncertain findings are marked. Confidence becomes the verifier's.
   - Duplicates are removed by (path, line range overlap, category, title embedding similarity).
   - Findings that repeat an *existing* GitLab discussion are linked to it, not repeated.
8. **Summary.** A walkthrough per file, a risk level, a verdict (looks good, comments, or changes suggested), a test-coverage note, CI state with an explanation of the failed job (reusing the Triggers pipeline text), and unresolved human discussions.
9. **Done.** Cost and tokens are stored. A notification goes out. The review room gets a system message.

### Re-review on a new push

Each run stores `head_sha`. A new version (from polling, the webhook or "Review again") computes its scope:

- **Fast-forward:** `compare_refs(old_head, new_head)` and review only those hunks.
- **Force-push or rebase:** compare the file diffs of the two MR versions (a range-diff per file) and review only the hunks whose text changed.

Carry-over for each open finding, matched by fingerprint (path, normalized hunk text, title):

| Situation | New state |
|---|---|
| Line unchanged | Re-anchored, still open |
| Line changed or removed | `outdated`. The verifier checks whether it is fixed (`fixed` or still open). |

A person's resolve or dismiss always stands; a dismissed finding is never raised again with the same fingerprint.

**Without an MR:** a branch against its target, `from..to`, one commit, or a plain git repository uses the same pipeline through `compare_refs` and `file_at`. There is no discussion or CI step unless a pipeline exists for the sha.

## 4. Where reviews live, and posting back

### The review page `/code/:host/:project/mr/:iid` (also `/code/reviews/:id`)

- **Header:** MR title, branches, author, CI badge, state, versions dropdown ("Reviewed v3, latest v4: Review new commits"), cost (shown only to the requester and the owner), and **Open in GitLab** using the existing "GitLab address for links" setting.
- **Left:** a file tree with counts per severity, plus "Skipped (N)".
- **Centre:** Monaco's diff editor, made a shared component and lazy-loaded.
  - Extract `code-arena/monaco.ts` and the compare part of `editor.tsx` into `src/web/src/components/code-diff/`.
  - Each finding is a **view zone** under its line: severity, category, body, suggestion (an inner diff), **Apply**, **Resolve**, **Dismiss** (reason: false positive, won't fix, intended), **Reply**, **Ask Arena**, **Post to GitLab**.
  - Existing GitLab discussions show as grey zones.
  - The 1-hunk fallback for phones uses `canvas-diff.ts`.
- **Right:** the review room (chat) with the MR attached. A "Findings" tab filters by severity, state and category.
- **Thread per finding.** Replies are `review_comments`, with author, mentions and live updates through the room's event stream. **Ask Arena** in a thread runs a one-shot answer as the asker, with the finding, its code and Argus pinned. The asker pays.

### Posting back with the person's own token only

- **Your account → Code hosts → GitLab:** paste a personal access token, or use **Connect with GitLab** (OAuth).
  - OAuth needs a GitLab application. A *user* or *group owner* can create one, so no instance admin is needed. **Decision P1.**
  - The token is stored in `PersonCredentials` (`ToolId = "codehost:gitlab"`, encrypted).
  - It is checked on save with `GET /user` and `GET /personal_access_tokens/self`, which shows the scopes. It must belong to the same GitLab user Argus matched for the person; otherwise it is refused.
- **Post** (one finding, chosen findings, or the summary) shows a preview of the exact text. A click sends:
  - `POST /merge_requests/:iid/discussions` with `position` for inline findings, or `/notes` for the summary.
  - A footer: "From Arena's review (AI-assisted), posted by <name>". Wording is configurable.
- **Afterwards:**
  - `PostedDiscussionId` is stored.
  - Resolving the finding in Arena offers to resolve the discussion in GitLab with the same token.
  - Audit: `review.post` (target, finding ids, and no content).
- **Never** Argus's token. **Never** the bot token (`GitLab:BotToken`) for reviews. **Decision P2:** whether scheduled automatic reviews may post through a bot that an admin configures. My default is no: automatic reviews notify, and a person posts.
- GitLab enforces its own rights: a Reporter cannot comment on a locked MR, and that answer is shown.

## 5. The online code assistant (no install)

**`/code` home.** "Your projects" comes from Argus as the person, with recent ones first, search, and watched projects (starred). Each project page shows open MRs (from `mr_list`) and branches, with **Ask** and **Review**.

**Ask.**
- A chat conversation with `Kind = "code"` and `CodeScope = {host, project, ref|mr, sha}`. It is the ordinary chat, with a scope chip in the header.
- Argus tools are pinned: the default repo and ref are injected, and `file_at` and `grep_at` work on branches that are not indexed.
- Answers cite `path:line` links that open the file viewer, a Monaco read-only side panel, at that sha.
- Prompts: "explain this file or function", "where is X handled", "what calls Y", "what breaks if I change Z" (`change_impact`).

**Suggest a patch.**
- The model writes a fenced `diff` block, or calls a `propose_patch` tool so the patch is stored as a `code_patches` row.
- The page validates it with Argus `apply_check` at the sha and shows it in the shared diff component. Its actions:
  - **Download .patch**: `git format-patch` style, with a From line naming the person.
  - **Open a merge request**, with the person's token: create a branch from the sha (`POST /repository/branches`), commit (`POST /repository/commits` with the actions from `apply_check`), then open the MR. GitLab requires Developer, and the refusal is shown. Audit `patch.mr`.
  - **Open in Code Arena** (section 7).
- **Apply** on a review finding's suggestion does the same thing.

## 6. Rooms with code

These build on design-rooms.md: a room is a `Conversation` with members, the asker pays and the asker's policies apply.

- **Review room.** One room per review: `Kind = "review"`, `conversations.ReviewId`. It is created with the first review, with the requester as owner.
  - **The MR is attached** as a system block: metadata, summary, finding list with ids and states, CI state. It is refreshed on each run.
  - Messages may cite `#F12` for a finding.
- **General rooms** work as in the rooms design. A code room can attach one or more scopes (project, branch or MR).
- **Who may be in a code room.** A member must *currently* be able to read every attached project.
  - Checked on invite through Argus (`/review/access?email=&project=`), and re-checked on every room request through `RoomAccess` with a 10-minute cache.
  - A person who loses GitLab access gets 404, and their open streams close.
  - A group added as members includes only the people who pass. The members panel shows the others as "cannot see project X".
- **Argus tools in code rooms.** Personal tools are **on** in code rooms, pinned to the attached projects only.
  - The rooms design turns them off by default because answers could show what the asker sees and others do not.
  - Here every member can already read those projects, so the answer cannot leak beyond them.
  - Unpinned Argus (other repositories) stays off.
- **Mentions** (`@Sara`, `@Arena`), live events, typing, queue and read markers work as in the rooms design. A mention on a finding thread notifies too.
- **Admin setting:** "Private MR rooms only for project members" is always on and cannot be turned off.

## 7. Integrations

### Code Arena

- **`/review`**
  - With no argument: reviews the local diff (staged plus unstaged, or `--base main`) with CA's own agent, using the **same review prompt** served by `GET /api/code-arena/review-prompt`.
  - The findings appear as Problems with severity, and as inline Monaco comments (decorations and view zones, from the same shared component).
- **`/review !42`, `/review <MR URL>`, `/review base..head`:** calls Arena's review on the server, so the person pays and gets one shared review. Progress streams through MCP `progressToken` (parity row 25).
- **`code-arena review open <id>`**, also the IDE's command "Open Review…":
  - fetches the findings and checks out the MR locally with the person's own git credentials (`git fetch origin merge-requests/42/head`);
  - shows the findings inline;
  - **Apply suggestion** applies the patch to the working tree through the compare view;
  - resolve and dismiss sync back through `PATCH /api/reviews/findings/:id` (key-authenticated, as `/api/code-arena` is).
- **"Open in Code Arena" from the web.** **Decision C1:** a registered URL scheme (`arena-code://review/<id>`), or a copyable `code-arena review open <id>` command. The scheme needs per-OS registration, Windows included, in the desktop window work.

### Arena MCP tools

Served to agents and to the chat when the person's rules allow:

| Tool | What it does |
|---|---|
| `list_mrs(project, state?, author?, mine?)` | Lists merge requests |
| `review_mr(project, iid, wait_seconds?)` | Starts a review or returns a running one; progress; findings when done within the wait, else the id |
| `review_range(project, from, to)` | Reviews a range without an MR |
| `get_review(id)` | Summary plus findings |
| `update_finding(id, state, reason?)` | Resolve, dismiss and so on |
| `ask_code(project, ref, question)` | Optional |

Each call is audited (`mcp.call`), and spend goes to the caller.

### Notifications

New `News` kinds:
- `review`: done or failed, to the requester;
- `mr`: a new MR in a project you watch, or someone asked you to review;
- `finding`: a reply or mention in a thread, or your finding was posted;
- `room`: per the rooms design.

Each person sets a level per watched project. Web Push and email work as for scheduled tasks.

### Scheduled and automatic reviews

A project review policy (Owner = the person who pays, or a team account as in ci.md):
- **Triggers:** on open, on new commits, when draft becomes ready, or by cron (for example a nightly review of `main`'s last day as a range).
- **Filters:** target branches, paths to ignore, smallest and largest size.
- **Settings:** model, extra instructions, who is notified, and the room audience (project members only).
- The existing scheduled tasks stay as they are. The policy is a new, typed thing, not a task prompt.

## 10. Credits, safeguards, audit, retention

**Credits.**
- The requester pays for a manual run and its re-reviews, and the asker pays for room and thread questions. A policy run is paid by its owner. MCP and Code Arena calls are paid by the caller.
- Charged as the **chat** kind, with `metadata.feature = "review"` on the gateway request so usage and chargeback can split it out. **Decision K1:** a new `Review` credit kind (Credits.cs gets a sixth kind, plus a group column).
- Checked before each model call. A run that runs out of credit stops with a partial result marked as partial.
- An estimate is shown before large runs.

**Safeguards.**
- Secret scanning on diffs creates findings and masks the model input, as in section 3.
- Job logs are masked. Personal data is masked by the group policy.
- The review model never gets write tools. The verifier is separate.
- Rate limits count by requester. Most review runs per person per hour is an admin setting (default 20).

**Audit (never content).**
- Reviews: `review.start`, `review.cancel`, `review.post`, `finding.state`
- Patches: `patch.mr`
- Code hosts: `codehost.token.set` and `codehost.token.remove`
- Policies: `review.policy.*`
- Rooms: `room.*` (rooms design)
- MCP: `mcp.call`
- Also `review.denied`: an access refusal, with the project and the reason.

**Retention.**
- Snapshots (`review_files.Diff`, comments with code) are kept for the shortest retention among the requester and the room members (rooms rule), capped by the admin setting **Keep review code for** (default 90 days).
- Afterwards the diff text goes: findings keep their text and anchors, and code is read live through Argus when someone with rights opens it.
- Legal hold soft-deletes. Deleting a person sets `CreatedById` and `AuthorId` to null ("Former member").
- A project removed from Argus makes its reviews read-only.
- The person's data export includes reviews they started and comments they wrote.

## 11. Access control per person and per group (phase A, first)

### 11.1 Concepts

**Permission:** a named capability in a fixed catalog in code (`Llm.Core/Access/Permissions.cs`).

Administrative permissions:
- People and groups: `people.read`, `people.manage`, `people.disable`, `groups.manage`
- Access itself: `access.read`, `access.manage`
- Models, tools, plugins and knowledge: `models.read`, `models.manage`, `models.load`, `tools.manage`, `plugins.manage`, `mcpservers.manage`, `knowledge.manage`
- Settings: `settings.read`, `settings.manage`, `signin.manage`
- Money and usage: `credits.manage`, `billing.read` (usage, chargeback), `usage.read`
- Oversight: `audit.read`, `logs.read`, `monitoring.read`, `alerts.manage`
- Data: `retention.manage`, `legalhold.manage`, `export.person` (eDiscovery), `storage.manage`
- Integrations: `bots.manage`, `tasks.manage.all`
- Argus: `argus.read`, `argus.manage` (repos, indexing, packs, webhook), `argus.explore`
- Rooms and reviews: `rooms.moderate`, `reviews.admin`

Feature permissions (what the default Member role holds):
- `feature.chat`, `feature.api_keys`, `feature.code_arena`, `feature.web_search`, `feature.pictures`, `feature.video`, `feature.speech`
- `feature.rooms.create`, `feature.share_links`, `feature.tasks`, `feature.assistants.share`, `feature.memory`
- `code.read` (assistant, Argus), `review.run`, `review.post_back`, `review.policy`

**Role:** a named set of permissions.
- Built-in roles are fixed. They can be cloned, not edited.
- Custom roles are made by `access.manage` holders.

| Built-in role | Permissions |
|---|---|
| Owner | everything |
| People admin | people.*, groups.manage, credits.manage scoped to their groups if scoped |
| Model admin | models.*, tools.manage, mcpservers.manage, plugins.manage |
| Billing | credits.manage, billing.read, usage.read |
| Auditor | every `*.read`, audit.read, logs.read; never a write |
| Argus admin | argus.* |
| Room moderator | rooms.moderate |
| Review admin | reviews.admin, review.policy for every project |
| Member | the feature set; given to everyone through the built-in group *Everyone* |

**Assignment:** (role, subject, scope?, expires?).
- The subject is a person or a group (app, directory or SCIM).
- An optional **scope** narrows a role:
  - People admin or Billing scoped to listed groups (delegated "group admins");
  - Argus admin scoped to repository path patterns (`team-a/**`);
  - Room moderator scoped to groups.
- An expiry is allowed: temporary elevation.

**Resource rule:** (effect allow|deny, subject person|group|role|everyone, resource kind + id or pattern, action, expires?, note).

| Resource kind | Actions |
|---|---|
| model, tool, mcp_server, plugin | use |
| knowledge_source | read |
| repo `host:path-glob` | code.read, review.run, review.see, review.resolve, review.post |
| feature | use (for per-resource overrides of feature permissions) |
| room | owner/member/viewer: stays per-room in `room_members`, never in rules |

**Ceilings that no rule can lift:**
1. A disabled person is denied everything.
2. **Code is visible only within the person's own host rights.** The effective repository right is `rules ∩ GitLab/GitHub rights`. Plain git has no host rights, so rules alone apply, with default deny.
3. Credits.
4. Group policies (retention, safeguards, rate limits). These are settings, not permissions, and keep their combine rules from settings.md.
5. Posting back additionally needs the person's own token, so the host enforces its own rights.

### 11.2 Evaluation (one function)

`Access.Check(principal, permission | (action, resource)) → Decision{allowed, because[]}`

1. Disabled → deny ("account disabled").
2. Ceilings (the host's code rights, scopes) → deny with the ceiling as the reason.
3. Collect the matching rules and assignments. Rank them by **specificity**:
   - person over group over role over everyone;
   - an exact resource over a pattern; a longer pattern over a shorter one.
4. **At the most specific level that has any match, deny wins over allow.** Less specific levels are ignored.
   - So a person-level allow can open what a group-level deny closes. That is intentional, for exceptions, and is shown in red in the checker.
   - **Decision A1:** the alternative is "any deny anywhere wins" (stricter, simpler to reason about). Pick one.
5. No match → the default:
   - admin permissions: deny;
   - feature permissions: what the *Everyone* group's roles say;
   - resources (models, tools and so on): deny, except that the migrated "Everyone" rules (11.5) keep today's behaviour.
6. **Owner** holds every permission and every resource allow, unless there is an explicit **person-level** deny on that resource. This keeps today's `Membership.May` (admins see every tool and model) without loss.

**Break-glass.**
- The bootstrap admin (`AuthOptions.AdminUserName`) always holds Owner. A rule or role change that would leave zero active Owners is refused.
- A person cannot remove their own `access.manage`.

**Caching.**
- A `Principal` is built once per request: person, groups (from `MembershipAsync`), effective permissions, compiled rules.
- It is kept per person and keyed by a global `access_version`. Each change bumps the version and `Replicas.Tell("access")` reaches every replica.
- A change therefore applies within one request everywhere.

### 11.3 One check everywhere

| Caller | How it checks |
|---|---|
| Endpoints | A `.RequirePermission("models.manage")` endpoint filter replaces `AdminEndpoints.Policy` (21 groups) and the 23 inline `IsAdmin` checks. Personal routes declare `.PersonOnly()`; anonymous ones declare `.AllowAnonymous("reason")`. |
| Resource lists | `ToolRegistry.ForAsync`, the model picker and `ModelPolicy.AllowedAsync`, knowledge readers and plugin lists call `Access.Check(use, resource)` instead of `Membership.May`. |
| Arena MCP | `McpTools.ServedAsync` uses the same registry call. Each `tools/call` checks again. |
| Gateway guardrail | `KeyAccess.ListForAsync` computes the model list from the check. `ApiOff` becomes a deny on `feature.api_keys`, so keys are blocked by `BlocksAsync`. Speech, picture and video routes check `feature.*` in the guardrail. |
| Argus | `/api/authz/key` (and the chat's email path, through a new `/api/authz/person?email=`) also returns a compact rules set: repository allow and deny patterns per action, plus `argus.read`, `argus.manage` and `argus.explore`. The answer is kept 5 minutes, as keys are; a change pings Argus (`POST /admin/access/changed`) to drop its cache. |

### 11.4 UI: Admin → Access (new; Admin → Groups stays for membership and policies)

- **Roles:** list, built-in and custom, with who holds each one. The editor is a permission checklist by area, each with a one-line description. Clone, delete (refused while assigned, or "reassign to…").
- **People** and **Groups** tabs:
  - assignments (role, scope, expiry) and rules where the subject is that person or group;
  - an **Effective permissions** view: every permission and resource with allowed or denied and its source chain ("allowed: role Model admin via group *ML team*; overridden by a person deny on model X").
  - The person page in Admin → People links here.
- **Rules:** a table filterable by subject, resource, action and effect, with notes and expiry.
- **Bulk:** choose many subjects × many resources × one effect and action, or assign a role to many.
  - Every bulk change and every single edit has a **dry run**: "changes the decision for 37 people: 35 gain, 2 lose", with a list.
  - Applied in one transaction, with one audit entry that lists every row.
  - Import and export as JSON or CSV.
- **Checker:** "Can [person] [action] [resource]?" answers yes or no with the ordered rule chain, the ceilings (GitLab level read live through Argus, credit left, disabled state), and links to each rule.
- **History:** every change with before and after (from `access_changes`). "Show access as of <date>" replays them for an investigation.
- **The resource pages** (Models, Tools, Knowledge, Plugins) keep their "Who may use it" picker. It now writes rules, so admins have one model of access whichever page they use.

### 11.5 Migration with no loss (one migration `AccessControl`, no backward compatibility kept)

   - `access_rules` (Id, Effect, SubjectKind, SubjectId, ResourceKind, Resource, Action, ExpiresAt, Note, CreatedById, CreatedAt)

   - Groups → allow each group;

   Then the columns are dropped.

## 14. Risks

- **Prompt injection through MR text and code.** Review tools are read-only, the verifier is separate, nothing posts automatically, and a person previews every post.
- **Leaks through rooms.** Code rooms admit only people with project rights, re-checked every 10 minutes and on each request. Argus is pinned to the room's projects.
- **Diffs in the database.** Code copied out of GitLab is a new place it lives. Retention and the keep-for-N-days setting bound it, and access is always re-checked against GitLab when it is read.
- **GitLab load.** One poll per watched project. Member lists are already kept 10 minutes. Diffs are read once per run and cached in the snapshot.
- **Migration risk in phase A.** The equivalence test against today's `Membership.May`, plus break-glass, guard against lockouts.
