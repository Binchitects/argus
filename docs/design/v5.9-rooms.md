# Design: multi-person chat rooms (design only, no code)

A room is an ordinary Conversation with members added. Whoever asks a question pays for the answer, and that person's policies and tools apply to it. Every room route checks access through one helper. All live events go over one events stream per room. I changed no repository files and no live state. I signed in once as admin for read-only GETs and ran read-only `psql`.

## 1. What exists today (evidence)

**Data model**
- `Conversation` has a single owner (`UserId`) and one shared `CurrentLeafId`, which marks the branch on screen (src/Llm.Core/Chat/ChatEntities.cs:8, :31).
- Deleting a person deletes their chats, because `conversations.UserId` cascades (src/Llm.Core/Data/AppDbContext.cs:97). Attachments cascade on `UserId` too (AppDbContext.cs:131).
- `ChatMessage` does not record who wrote it (ChatEntities.cs:67-122).
- `QueuedMessage` does not record whose message it is (src/Llm.Core/Chat/QueuedMessage.cs:8-20).
- `ChatShare` is a read-only link for the company or chosen groups, never for people signed out. The link id is random (ChatEntities.cs:224-248).
- `AnswerFeedback` is already unique per (MessageId, UserId), so several people can already rate one answer (src/Llm.Core/Chat/QualityEntities.cs:59).
- `CanvasVersion.Author` is a plain string (src/Llm.Core/Chat/Canvas.cs:33).
- Bot threads are one chat per thread *and person*, so they are no precedent for a shared chat (Integrations.cs:3-19).

**Access is owner-only everywhere**
- The `Owned()` check is `c.Id == id && c.UserId == me.Id` (src/Llm.Api/Chat/ChatEndpoints.cs:130).
- Helper uses: ChatEndpoints.cs ×14, CanvasEndpoints.cs ×8, QueuedMessages.cs ×4 (`OwnedAsync` :144-147), ChatEndpoints.Arena.cs ×1, AnswerCache.cs ×3. The stamp endpoint has its own inline check (:747).
- Other files with `Conversations…UserId ==` filters: ChatSearch, ChatHistory, CodeArenaSync (:80, :127, :159), DataExport (:33), Retention, StorageCleanups, QualityEndpoints.
- Live check, signed in as admin: GET on another person's chat, `/stamp`, `/stream` and `/share` all returned **404**. Not even an admin can open someone else's chat.

**People, groups and sign-in**
- `AppUser` has `Source` local/ldap/oidc, `DirectoryGroups`, `MemoryOff` and `LegalHoldSince` (src/Llm.Core/Identity/AppUser.cs).
- App, directory and SCIM groups live in one table (src/Llm.Core/Access/Groups.cs:10-62). `AccessService.MembershipAsync` resolves both kinds.
- People and group pickers exist already: `/api/sharing/people` returns name and username but no email, and `/api/sharing/groups` returns only your groups unless you are an admin (src/Llm.Api/Access/SharingEndpoints.cs:17-52). Live: both return 200.

**How answers run and stream**
- An answer is a background job: one per conversation (`TryAdd`, src/Llm.Api/Chat/AnswerJobs.cs:214-218), tied to a person (`Job.Person`, :58).
- A second ask while one is running gets **409 busy** (ChatEndpoints.cs:622-625).
- Streaming is server-sent events with a 15 s heartbeat (ChatEndpoints.cs:63, :771-790). A page that joins late gets the whole answer replayed (AnswerJobs.cs:138-197).
- An idle open chat polls `/stamp` every 4 s (src/web/src/pages/chat/api.ts:68-72; ChatEndpoints.cs:744-757). Live: an idle `/stream` returns 204 in 6 ms, and `/stamp` answers in 4-18 ms.
- With several replicas, a page on another replica sees the answer only once it is saved, not live (docs/architecture.md:191-195).
- Replicas talk over Postgres `pg_notify`, which opens a new connection per message and has an 8000-byte payload limit (src/Llm.Api/Operations/Replicas.cs:117-124). That suits small events, not tokens.
- The live stack runs a single `app` replica.

**Credits and usage**
- The gateway request names the person: `["user"] = email` (src/Llm.Api/Chat/ChatService.cs:330), plus the `X-LLM-User-Email` header (GatewayChat.cs:202).
- Spend is read per email (src/Llm.Api/Gateway/Credit.cs:20-27). The chat credit check runs per person (src/Llm.Api/Models/ModelCatalog.cs:958).
- The place in line and the answers-per-person limit go by `Job.Person` (AnswerJobs.cs:367; AnswerGate.cs:62, :197).
- So if the job's person is the asker, the asker pays.

**Policies tied to the person today**
- Safeguards use the strictest setting of the person's groups (src/Llm.Api/Safeguards/Safeguards.cs:64-88).
- The message rate limit counts by *conversation owner* (Safeguards.cs:118). In rooms that would miscount.
- Masking personal data uses the asker's policy for the whole history (ChatService.cs:1193).
- Retention takes the shortest of the person's groups (src/Llm.Api/Retention/Retention.cs:37-42).

**Personal data that would leak to other members**
- The asker's memories go into the system prompt (ChatService.cs:244; Memories.cs:50).
- Knowledge search uses the asker's readers (src/Llm.Api/Knowledge/KnowledgeTool.cs:27-50).
- Some tools act as the asker:
  - Argus sends the asker's email (ArgusMcp.cs:488, :497).
  - MCP servers can be set to send the asker's email (ToolRegistry.cs:81).
  - Plugins that sign in per person use the asker's token (ToolRegistry.cs:53-70).

**Code that would break with members**
- The message queue starts answers as the owner and drops files that are not the owner's (QueuedMessages.cs:48, :55).
- Only the owner can answer ask-before-running tool prompts (ChatEndpoints.cs:414-422).
- The retention sweep counts a file as used only in the person's *own* chats (Retention.cs:119-133). A member's file in someone else's room would be erased.
- Deleting a person cascades away their rooms (PeopleService.cs:305 → AppDbContext.cs:97).
- History building loads files without filtering by owner (ChatService.cs:1187), which is fine for rooms.

**Live database (read-only):** 2 people, 1 group with 0 members, 235 conversations, 1106 messages, 0 shares, 0 queued.

## 2. Design decisions

**Model**
- A room is a `Conversation` with `Kind = "room"`; `Conversation.UserId` is its owner.
- Members are rows of their own; whole groups can be added as live grants.
- Every route that reads or writes a conversation goes through one `RoomAccess.FindAsync(db, id, me, Need.Read|Write|Manage)` helper instead of `Owned()`. A room you may not open returns 404, as share links do.

**Roles**
- **Owner:** settings (model, tools, instructions, assistant, answer mode, tools that act as the asker), invite, remove, change roles, links, rename, delete, hand ownership to someone else. The owner cannot leave without handing it over.
- **Member:** read, ask, send people-only messages, attach files, edit the canvas, compact, fork. Edits only their own questions and regenerates only answers to them. Stops or says "Answer now" on their own answers (the owner can too). Allows or denies only their own tool calls.
- **Viewer:** read, watch live, rate answers, fork into their own chat.
- A setting lets the owner allow members to invite.

**Invites**
- The owner adds people by name, email or username (existing picker) or adds a group (existing picker). Groups are live: whoever is in the group now is in the room.
- Added people join at once and get a bell notice; they can leave.
- Invite links work like `ChatShare` links: random id, signed-in only, reach company or chosen groups, role, expiry, use limit, revoke. Joining needs a click.
- Turning a private chat into a room shows a confirmation that the earlier messages become visible to members.

**Live**
- New `GET /api/rooms/{id}/events` server-sent events stream, served by an in-memory `RoomHub` singleton with a channel per watcher, like `Job`.
- Events: message, answer-started (who asked, which question), answer-ended, queue, typing, presence, members, settings.
- Answer tokens still come from `/conversations/{id}/stream`, now open to members; the page opens it on answer-started.
- Typing: `POST …/typing`, sent at most every 3 s by the page, expires after 6 s.
- Each person's message carries their name. Answers say "asked by X". The stamp poll stays as a fallback.

**Who pays: the asker**
- `Job.Person` is the asker. The gateway `user` field and header carry the asker's email.
- The asker's credits apply, and chargeback goes to the asker's groups and cost centre. The same holds for picture and video tools, compaction and titles.
- The cost of each answer is shown only to the asker and the owner.

**Whose policy: the asker's**
- **Model:** the room's model if the asker may use it. Otherwise the asker's default model, with a notice. An optional model choice per ask.
- **Tools:** the room's tools that the asker may also use. This intersection exists already: `ToolRegistry.Chosen(conversation.Tools, allowed)` in ChatService.
- **Safeguards:** each author's own message is checked by their own policy when written.
- **Masking personal data in the history:** the strictest policy among current members.
- **Rate limits:** counted by the message's author (new `AuthorId`).
- **Assistant:** each asker must be able to use the room's assistant (`Assistants.LostAsync`). Inviting someone who cannot use it warns the owner; that person can read but not ask.

**Privacy**
- No memory block and no memory tool in rooms.
- Knowledge results are limited to sources that every current member may read (readers checked per member).
- "Personal tools" (Argus, MCP servers with an email header, plugins that sign in per person) are off in rooms by default:
  - The owner may turn them on, with a banner: "answers can show what the asker can see".
  - Each result is labelled with whose identity it ran as.
  - An admin can forbid them in rooms altogether.
- Reason: another member's message can steer the asker's tools (prompt injection between members).
- Emails are never shown; only display names.

**Model input**
- Each person's turn starts with the author's display name. The system note lists members by name and says who is asking.
- Consecutive user turns are merged into one, because some chat templates require user and assistant turns to alternate.

**Answer mode** (room setting)
- "Every message is answered" (default): the composer has a "Just say it" switch for messages meant only for people.
- "Only when @Arena": the model answers only when mentioned.

**Concurrency**
- Still one answer at a time per room.
- In a room, an ask while busy is queued (202) instead of refused with 409. The queued entry records its author and starts as that author.
- Credits are checked when it starts; a refusal goes to the author.
- People-only messages sent during an answer are queued and saved in order after it.
- Limits: 20 queued per room, 3 per member. Members cancel their own; the owner can cancel or reorder any.

**Branches**
- `CurrentLeafId` is the room's shared head.
- Editing or regenerating moves the head for everyone, and the timeline says who did it.
- Browsing sibling branches is local to the page; changing the shown branch on the server is owner-only.
- Fork works as today (files are copied).

**Mentions and notifications**
- Mentions are stored as `ChatMessage.Mentions` (uuid[]).
- The bell gets a new kind, `News("room", …)`, with a link to the message, plus Web Push.
- Notify level per member: all / mentions and answers to me (default) / none.
- The existing "answer ended while nobody watched" notice already goes to `job.Person`, i.e. the asker.

**Leaving and removal**
- Access ends at once and the hub closes that person's open streams.
- Their messages stay, with their name. Their files stay readable by the room.
- When a person's account is deleted: ownership passes to the longest-standing member first (or the room is deleted if there is none). Their messages become "Former member" (`AuthorId` set null). Their files go with their account (cascade).

**Retention**
- A room is kept for the shortest retention among current members, the owner included.
- If any member or past author is on legal hold, the room is soft-deleted (`DeletedAt`) rather than erased.
- The file sweep counts files used in rooms the person is in or wrote in.
- The room header says "Kept N days (shortest of its members')". The invite dialog warns when the invitee would shorten it.

**Audit** (never message content, as `chat.share` does today)
- `room.create`, `room.invite`, `room.join`, `room.leave`, `room.remove`, `room.role`, `room.transfer`, `room.link.create`, `room.link.revoke`, `room.settings`, `room.delete`.

**Export**
- Room export for owner and members: Markdown or zip with author names.
- A person's own data export adds the room messages they wrote and the answers to them.

**Admin settings** (Settings → Chat → Rooms)
- Who may create rooms (Everyone / Admins / Groups).
- Most members (50).
- Invite links on or off.
- Tools acting as the asker in rooms: never / owner decides.

**Code Arena:** rooms are not synced to Code Arena in the first version. CodeArenaSync.cs:80 gets a filter so rooms are left out.

**Several replicas**
- Small room events fan out through `Replicas.Tell("room", …)`.
- Live answers relay only while another replica has watchers: the replica writing the answer batches it every 250 ms into notifications under 7 KB, and the other replica keeps a read-only mirror of the job.
- The live single-replica stack needs none of this.

## 3. Database migration "Rooms"

- **conversations:** add `Kind` varchar(16) null, `AnswerMode` varchar(16) null, `MembersInvite` bool default false, `PersonalTools` bool default false.
- **chat_messages:**
  - add `AuthorId` uuid null, foreign key to people with ON DELETE SET NULL. On a person's message it is the writer; on answers and tool rows it is the asker.
  - add `ForPeople` bool default false, and `Mentions` uuid[] default `'{}'`.
  - index (`AuthorId`, `CreatedAt`) filtered to `Role = 'user'`.
  - backfill: set `AuthorId` from the conversation's `UserId`.
- **queued_messages:** add `UserId` uuid not null (backfilled from the conversation, cascade), and `ForPeople` bool.
- **room_members:** (`ConversationId`, `UserId`) primary key; `Role`, `AddedById`, `AddedAt`, `LastReadAt`, `Notify`, `ArchivedAt`; cascade on both; index on `UserId`.
- **room_groups:** (`ConversationId`, `GroupId`) primary key; `Role`; cascade on both.
- **room_invites:** `Id` random uuid; `ConversationId`, `CreatedById`, `Role`, `Reach`, `Groups` uuid[], `ExpiresAt`, `MaxUses`, `Uses`, `CreatedAt`; index on `ConversationId`.

## 4. Endpoints

**New, under /api/rooms**
- `GET /api/rooms` — my rooms, with unread count, answering flag and my role.
- `POST /api/rooms` — create, with title, members, groups, model, tools, assistant.
- `POST /api/chat/conversations/{id}/room` — turn a private chat into a room.
- Members:
  - `GET /api/rooms/{id}/members`
  - `POST /api/rooms/{id}/members`
  - `PUT /api/rooms/{id}/members/{userId}` — change role
  - `DELETE /api/rooms/{id}/members/{userId}` — remove, or leave when it is yourself
  - `PUT /api/rooms/{id}/owner` — hand over ownership
- Settings: `PATCH /api/rooms/{id}` (answer mode, members may invite, personal tools); `PUT /api/rooms/{id}/me` (my notify level, archived).
- Links:
  - `GET /api/rooms/{id}/links`
  - `POST /api/rooms/{id}/links`
  - `DELETE /api/rooms/{id}/links/{linkId}`
  - `GET /api/rooms/join/{token}` — preview
  - `POST /api/rooms/join/{token}` — join
- Live: `GET /api/rooms/{id}/events` (server-sent events), `POST /api/rooms/{id}/typing`, `POST /api/rooms/{id}/read`.
- `GET /api/rooms/{id}/export`

**Changed**
- All `/api/chat/conversations/{id}/*` routes (and canvases, queue, compare, attachments) check access through `RoomAccess`.
- `MayReadFileAsync` (ShareEndpoints.cs:228) also lets room members read the room's files.
- `NewMessage` gains `ForPeople`, `Mentions` and an optional `Model`.
- Message shapes and the "question" stream event gain `author {id, name}`.

## 6. Tests

New tests/Llm.Tests/RoomTests.cs, using `FakeModel.Requests` (body and headers) and the ShareTests person and group helpers. Each item is one behaviour to prove:

1. Non-members get 404 on every route (chat, stamp, stream, events, files, canvases, queue).
2. A viewer gets 403 on send and upload.
3. A member's ask carries `user` and `X-LLM-User-Email` = member, and the member's credit refusal blocks only their own ask.
4. A room model the member may not use falls back to their default, with a notice.
5. The tools offered are the room's and the asker's intersection; only the asker may decide tool approvals.
6. No memory block or memory tool in rooms.
7. Knowledge results are limited to what all members may read.
8. Personal tools are off by default (FakeArgus not called) and on when the owner allows them.
9. Two asks at once: one 202 queued, which starts as its author; order holds; people-only messages are saved after the answer.
10. The events stream delivers message, typing and answer-started to another member; a late watcher gets the replay.
11. History carries author labels and merges consecutive user turns.
12. Rate limits count by `AuthorId`; masking personal data uses the strictest member's policy.
13. Retention: the room goes at the shortest member retention; a hold soft-deletes it; a member's file used in a room survives the sweep.
14. A removed member gets 404 at once and their stream is closed; their messages stay.
15. Invite links: reach, expiry, use limit, revoke, never signed out.
16. Deleting the owner hands the room over; a deleted author shows as "Former member".
17. Audit rows contain no content.
18. ScaleOutTests: events fan out and answers relay across two replicas.
19. Code Arena sync leaves rooms out.

Web (vitest): Rooms section in the sidebar, members and invite dialogs, author rendering, mentions, viewer composer, approval waiting state.

## 8. Risks to settle

- **Prompt injection between members.** This is why personal tools are off by default; tools that act (rather than read) should ask before running in rooms.
- **Retention.** When a member with short retention joins, the whole room's retention gets shorter. The invite dialog warns, but the owner may prefer to refuse such invites.
- **Answer cost.** Cost is visible only to the asker and the owner.
